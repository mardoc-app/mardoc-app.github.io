# M1 owner guide: Sign in with GitHub, stage 1

This guide is how you check M1 yourself. Part A is one command. Part B is a
real sign-in on your own machine with a development GitHub App, one screen at
a time. Part C points to the production steps.

Plan: [WP-8](../docs/plan/WP-8.md). Design: [github-sign-in](../docs/design/github-sign-in/design.md).
The latest automated run is [m1-demo-report.md](m1-demo-report.md).

## Part A: the automated demo

From the repo root, with dependencies installed once
(`npm ci` and `npm --prefix worker ci`):

```sh
npm run demo -- m1
```

It takes about two minutes and contacts neither GitHub nor Cloudflare. It
runs five steps and writes `demos/m1-demo-report.md`:

| Step | What runs | Proves |
|---|---|---|
| 1 | `next build` | The static export in `out/` |
| 2 | `e2e/sign-in-flow`, `sign-in-ui`, `sign-in-stage1-gate` and `sign-in-journeys` specs, desktop and mobile, with GitHub and `/api/auth/*` mocked | Every journey (T-31), the stage 1 gate: no token in web storage, URLs, history or performance entries (T-10, T-11) |
| 3 | `e2e/sign-in-real-worker.spec.ts` in Chromium against the real Worker module under `wrangler dev`, GitHub stubbed (`dev/local-auth/`) | The real callback page posts to the real tab, its CSP runs only its own script, the pop-up closes, the `__Secure-` cookie works on `http://localhost` (T-32) |
| 4 | The same spec in Firefox | As step 3, in Firefox |
| 5 | Looks for `dev/` in `out/` and in the Worker bundle (`wrangler deploy --dry-run`, which uploads nothing) | The local harness ships nowhere |

**PASS looks like:** the terminal ends with the report, and its first line
reads `- **Result: PASS**`. Every step row says PASS. In step 2 the four cases
named `t31_token_option_from_...` show a cross: they are expected failures
for a known defect (backlog M1-5) and count as passed.

**If it is wrong:**

- `Result: PASS (Firefox BLOCKED)`: Playwright's Firefox is missing. Run
  `npx playwright install firefox`, then the demo again.
- Port 8787 or 3000 is busy: run
  `REAL_WORKER_PORT=8790 PLAYWRIGHT_PORT=3108 npm run demo -- m1`.
- Step 3 fails in `beforeAll` with "the harness must run with STUB_GITHUB=1":
  your own `npm run dev:auth` from Part B is still running on 8787. Stop it
  (Ctrl+C) and run the demo again.
- Anything else that says FAIL: keep the terminal output and the report, and
  record it as an AT-n row (end of this guide).

## Part B: a real sign-in at localhost

You need: a GitHub account, a test repository on it with at least one `.md`
file, and about 15 minutes. Nothing here touches `mardoc.app` or Cloudflare.
Below, `<login>` is your GitHub login and `<test-repo>` is the test
repository's name.

### B1. Register the development GitHub App

1. Open `https://github.com/settings/apps/new`. You see **Register new GitHub
   App**.
2. Fill in exactly:

   | Field | Value |
   |---|---|
   | GitHub App name | `MarDoc Dev (<login>)` |
   | Homepage URL | `http://localhost:8787` |
   | Callback URL | `http://localhost:8787/api/auth/callback` |
   | Expire user authorization tokens | **checked** |
   | Request user authorization (OAuth) during installation | **unchecked** |
   | Enable Device Flow | unchecked |
   | Setup URL | empty |
   | Webhook → Active | **unchecked** |
   | Repository permissions → Contents | **Read and write** |
   | Repository permissions → Pull requests | **Read and write** |
   | Repository permissions → Metadata | **Read-only** (GitHub sets it) |
   | Account permissions | none |
   | Where can this GitHub App be installed? | **Only on this account** |

3. Click **Create GitHub App**. You see the App's **General** page with
   `Client ID` (it starts with `Iv`). Copy it somewhere for B3.
4. On the same page, under **Client secrets**, click **Generate a new client
   secret**. GitHub shows the secret once. Keep the page open for B2.
5. Note the App's public link at the top of the page,
   `https://github.com/apps/<slug>`. The `<slug>` is used in B3.
6. In the left menu click **Install App**, then **Install** next to `<login>`.
   Choose **Only select repositories**, pick `<test-repo>`, click **Install**.
   You land on the installation's settings page listing `<test-repo>`.

**If it is wrong:** GitHub says the name is taken: add a suffix, for example
`MarDoc Dev (<login>) 2`; nothing else depends on the name.

### B2. Put the client secret where only the harness reads it

1. In your editor, create the file `dev/local-auth/.dev.vars` in the repo
   with one line: `CLIENT_SECRET=<the secret from B1 step 4>`. Do not type
   the secret into the shell, so it stays out of your shell history.
2. Check git ignores it:

   ```sh
   git check-ignore -v dev/local-auth/.dev.vars
   git status --short dev/
   ```

   The first prints `dev/local-auth/.gitignore:2:.dev.vars	dev/local-auth/.dev.vars`.
   The second prints nothing.

**If it is wrong:** if `git status` lists `.dev.vars`, delete the file and
stop; report it as an AT-n row. Never commit it.

### B3. Start the harness

1. Check port 8787 is free: `lsof -iTCP:8787 -sTCP:LISTEN` prints nothing.
2. Run, with the Client ID and slug from B1:

   ```sh
   NEXT_PUBLIC_GITHUB_APP_SLUG=<slug> npm run dev:auth -- --var CLIENT_ID:<client id>
   ```

3. After the build (about 30 s) the terminal shows
   `Using secrets defined in dev/local-auth/.dev.vars`, then a bindings table:

   ```text
   env.APP_ORIGIN ("http://localhost:8787")         Environment Variable      local
   env.CLIENT_ID ("(hidden)")                       Environment Variable      local
   env.CLIENT_SECRET ("(hidden)")                   Environment Variable      local
   env.STUB_GITHUB ("(hidden)")                     Environment Variable      local
   ```

   and last `Ready on http://localhost:8787`.

**If it is wrong:** no `Using secrets defined in dev/local-auth/.dev.vars`
line or no `env.CLIENT_SECRET` row: `.dev.vars` is not in `dev/local-auth/`
or is misspelt. 8787 busy: stop whatever holds it (the
callback URL on the App names 8787, so a different port means changing the
App too, then `--port <p> --var APP_ORIGIN:http://localhost:<p>`).

### B4. Sign in

1. Open `http://localhost:8787` in Chrome. You see MarDoc in demo mode with
   sample data.
2. Click the gear (**Settings**) at the top right. The **GitHub Connection**
   tab shows a **Sign in with GitHub** button first and a **Use a personal
   access token** link below it.
3. Click **Sign in with GitHub**. A small window opens on `github.com`
   showing **Authorize MarDoc Dev (`<login>`)** (sign in to GitHub first if
   it asks).
4. Click **Authorize MarDoc Dev (`<login>`)**. The small window closes by
   itself within about a second.
5. Settings now shows **Signed in with GitHub as `<login>`** and, under it,
   "Signed in through the MarDoc GitHub App".
6. Click the **Repository** tab. The list shows `<login>/<test-repo>` and no
   other repository (F-40). Click it. Settings closes and the file tree of
   `<test-repo>` appears. Open a `.md` file; it renders.

Note two numbers for T-26: the clicks from step 2 to step 5 (expected: three,
Settings, Sign in with GitHub and Authorize, plus GitHub's own sign-in if it
asked), and the seconds from clicking Authorize to seeing "Signed in with
GitHub as `<login>`" (NF-16 asks at most 3 s on the live site; localhost is
a first reading).

**If it is wrong:**

| You see | Likely cause | Do |
|---|---|---|
| The small window says "Sign-in must start from MarDoc." | The URL was opened directly | Start again from Settings |
| GitHub says "The redirect_uri is not associated with this application" | The Callback URL in B1 differs | Fix it to `http://localhost:8787/api/auth/callback` |
| Settings: "Sign-in could not be verified. Check that cookies are allowed for mardoc.app, then try again." | The attempt cookie was blocked | Allow cookies for `localhost`; record the browser |
| Settings: "Sign-in is misconfigured." | Expiring tokens are off on the App | Turn on **Expire user authorization tokens** |
| Settings: "GitHub did not answer. Try again." | Wrong secret, or the bindings table had no `CLIENT_SECRET` | Generate a new secret, update `.dev.vars`, restart B3 |
| Settings: "Sign-in with GitHub is unavailable right now." | The harness is not running | Restart B3 |
| The small window stays on "Finishing sign-in…" or says "Return to MarDoc and try again." | The window lost its link to the MarDoc tab (A-10) | Record the browser and version as an AT-n row; this matters for SP-3 |
| The Repository tab lists repositories you did not install on | A-16 does not hold | Record it as an AT-n row |

### B5. Reload ends the session

1. With the `.md` file open, press Cmd+R (Ctrl+R).
2. A strip above the document reads **Sign in again to open `<path of the
   file>`**, with **Sign in again** and **Continue without signing in**. The
   main pane names the same file instead of showing sample data. The address
   bar still ends with the file's route.
3. Click **Sign in again**. The small window opens and usually closes at once
   without asking (GitHub remembers you). The file opens again.

**If it is wrong:** the page shows sample data with no strip, or opens the
file without asking: record it as an AT-n row (F-31, F-32, F-37).

### B6. Disconnect

1. Settings → **GitHub Connection** → **Disconnect**.
2. The tab shows **Sign in with GitHub** again, and the strip is gone.
3. Reload. No **Sign in again** strip appears; MarDoc is in demo mode.
4. Optional: `https://github.com/settings/apps/authorizations` still lists
   **MarDoc Dev (`<login>`)**. Disconnect revokes the token only, not your
   authorisation (A-14).

### B7. Stop and clean up

1. Press Ctrl+C in the terminal running the harness.
2. If you are done with local sign-in, delete `dev/local-auth/.dev.vars` and,
   on the App's **General** page, delete the client secret. Keep the App if
   you will use it again.

## Part C: production

Sign-in reaches `mardoc.app` only after SP-3 passes. The steps, in order:

1. SP-3's runbook in [sp-3-callback-opener.md](../docs/spikes/sp-3-callback-opener.md#owner-runbook),
   with its disposable Worker, in the five browsers.
2. The production runbook in [worker/README.md](../worker/README.md#production-runbook-owner):
   register the production App (step 0), tag, secret, deploy, route, logs
   off, usage alert at 50%, probe (T-25), one real sign-in (T-26), and the
   Free plan and request-count check at each milestone close (T-29).
3. Secret rotation, yearly and on any suspected leak: the same README
   (NF-21), with SP-2 ([sp-2-client-secret-rotation.md](../docs/spikes/sp-2-client-secret-rotation.md))
   deciding whether rotation can avoid failed sign-ins.
