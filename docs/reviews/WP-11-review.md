## Why this work matters

The owner's complaint (2026-10-29) is that every folder opens by itself on each visit. A large repository then turns into a long scroll, and folders the reader opened are forgotten on every file open (the old `useState(depth < 2)` reset whenever a row remounted). WP-11 should give a repository that starts collapsed, a selected file that is revealed and scrolled into view, and open/closed state that is remembered per repository **and branch**. The risk the slice plan calls riskiest is state written under a ref that is not the tree the reader is looking at. Both bugs below are cases of that risk which the guessed-`main` fix does not cover.

## Verdict

**FAIL.** The structure is sound: a pure store with bounds that never throws, one shared set for the two Sidebars on phones, a `treeRef` taken from the loaded tree rather than `selectedBranch`, and e2e edits that only add a folder-open step. But two realistic navigation sequences write folder state under the wrong branch (WP11R-1 and WP11R-2, both reproduced). That breaks the "per repository and branch" part of F-82. The tests drive the hook with a hand-set `treeRef`, never through app-context, so they cannot catch either bug (WP11R-3). Fix WP11R-1 to WP11R-4 before owner acceptance. WP11R-5 and WP11R-6 are optional.

## Checked and found sound

**expansion-store (`src/lib/expansion-store.ts`)**
- The store is a parameter, and the file imports only `tree-expansion`. `f82_store_uses_only_the_given_store` stubs `localStorage` with a throwing proxy, so a hidden global read would fail it.
- Bounds: 20 entries, with the oldest dropped on save. A re-saved key is deleted and re-inserted, so it becomes newest, and the test checks this. Keys of the form `owner/repo@ref` always contain `/` and `@`, so JS's ordering of integer-like keys cannot reorder them. Paths are capped at 200 through `parse`, both when loading and when re-saving other entries, so a tampered value of 500 paths is cut down on the next save.
- Never throws: `readAll`, `load` and `save` each catch. Invalid JSON, `null`, numbers, strings, arrays, non-array entries and mixed-type arrays all load as an empty or string-only set. A store that throws on read or write is silent. Saving over corrupt data replaces it.
- The behaviour matches the L2 text ("corrupt or oversized storage parses to a bounded set without throwing"). The slice plan's wording "oversized loads as an empty set" is looser than the L2 and the code. The L2 page is the authority here.

**treeRef in app-context**
- It is set only when `isCurrent()` is true, in the same batch as `setRepoFiles(files)`, so a stale tree response cannot set it.
- It is cleared on a failed tree or revision fetch, on a repo change in `activateRepo`, on `resetToNoCredential`, on "continue without signing in", and on the "sign-in-again" start. `resetForCredentialChange` leaves it set but makes `currentRepo` null, and the hook then uses its memory key, so nothing persists. The next `activateRepo` counts as a repo change and clears it.
- The resolved default branch is used in `loadRepoRoot` (`ref` comes after `fetchDefaultBranch`). The embed path's `branch || "main"` is the ref actually fetched, so the tree really is `main`, or the fetch fails and `treeRef` stays null.
- Same-repo branch switch through `setSelectedBranch`: `selectedFile` becomes null in the same batch, so nothing is revealed under the old ref. The old tree stays on screen under the old key until the new one arrives, and that is consistent. The cross-branch **link** case is not (WP11R-1).
- In demo mode and for local or new files, `treeRef` is null or the path is virtual (`__local__/`, `__new__/`), so `reveal` is a no-op or works in memory only. Nothing is written.

**The shared hook (`src/lib/use-tree-expansion.ts`)**
- Snapshot stability: `getSnapshot` returns `entry.set`, and that reference changes only in `commit`. React's double `getSnapshot` call and the StrictMode double render return the same object. `getServerSnapshot` returns a constant `EMPTY`, which is right for the static export's hydration.
- The two Sidebars share one entry and one listener set. The second instance's reveal effect sees an unchanged size and does not write again. `f82_two_sidebars_share_one_state` checks that writes equal toggles.
- `reveal` only adds paths, so comparing sizes is a valid "changed" test. A visit with no selection and no carry-over writes nothing.
- The stored set loads once per key per session. Every save re-reads storage, so entries written by other keys or by another tab are kept.

**Sidebar**
- `FileTreeItem` is controlled: `expandedSet` and `onToggle` replace its own state, folder rows carry `aria-expanded`, and the old `useState(depth < 2)` is gone (F-80).
- The scroll effect runs after the row exists, including when the tree arrives after the file and when the Files tab or a collapsed sidebar reopens. On phones the drawer's Sidebar stays mounted off-canvas (`MobileDrawer` translates it rather than unmounting), so it scrolls when its row mounts and the position is already right when the drawer opens. The hidden desktop copy's `scrollIntoView` on a `display:none` element does nothing.
- Collapse all (F-83) saves an empty set and keeps other branches' entries (`f83_collapse_all_saves_an_empty_set`). The selected file is not re-revealed until the selection changes, which matches Q-RB-1. The button is inside `!isEmbedded`, and embed mode does not show the repository Files tab, so the condition "shown when the repository tree is visible" holds.

**e2e edits to existing specs**
- `critical-flows`, `navigation-routing`, `sign-in-ui`, `toolbar-parity` and the `openMarkdownFile` and `openHtmlFile` helpers only add `openTreeFolder(page, "docs")`. No assertion was removed or loosened. The `sign-in-ui` check for demo data still asserts that `getting-started.md` is visible. `openTreeFolder` clicks only when the folder is closed and then asserts `aria-expanded="true"`. The demo tree (`mock-data.ts`) keeps every non-README, non-CHANGELOG file under `docs/`, so the helper's README/CHANGELOG test is correct for today's data.
- `per-file-comments` and `pr-image-stability`, listed as affected in the plan, use the PR file tree and needed no change.

**New e2e specs prove what F-80 to F-83 state**
- F-80: three top-level folder rows, all `aria-expanded="false"`.
- F-81: exactly two open folders (`a`, `a/b`), the `c.md` row highlighted, and a scroll container with `scrollTop > 0` that holds the row. The 40 filler files make sure the scroll actually happened.
- F-82: open `x`, open `README.md`, reload: exactly one folder open and `y.md` visible.
- F-83: three open folders, click, zero open, then a reload from the repo root with zero still open. Navigating to the repo root first means a deep link cannot re-reveal the folders and mask a failed save.

**Compliance**
- The files, order and increments match the slice plan. The hook was added under the plan's "design gap" section, and Q-RB-5 is recorded as decided on the L2 page.
- Tests carry the IDs: `f80_`, `f81_`, `f82_` and `f83_`.
