# WP-12 slice plan: PR file links by path (#142)

## Context

A PR file link names the file by its position (`#/o/r/pull/12/files/3`). When the PR gains or loses a file, the numbers shift and the link opens the wrong file. WP-12 builds F-84 and F-85 from the accepted L2 page `docs/design/l2-links-routing.html`, on top of WP-10's pure `src/lib/routing/route.ts` (merged: `parseHash` already reads `file/<path>`, `buildRoute` writes it, `resolvePRFile` matches it).

- F-84: a PR file link names the file by path (`#/o/r/pull/N/file/<path>`), and the app writes that form. e2e: a cold load of a path link opens that file after the PR files load.
- F-85: a legacy index link (`/pull/N/files/<idx>`) still opens the file at that index. e2e: a cold load of `/files/1` opens the second file; the address bar then shows the path form.

Today (main `6b2a8d9`): `hash-router.ts` turns path links into `{type:"none"}` ("Invalid document link."); `_openPRInternal` writes the index hash before the manifest arrives (`app-context.tsx:1018`); `setHash` assigns `window.location.hash` directly (`:296-299`); other code reads or listens to the address bar itself (`page.tsx:73-74`, `SignInBanner.tsx:35`, `PRDetail.tsx:81-105, 530, 649`), and DiffViewer builds index links for HTML review links (`DiffViewer.tsx:375`).

## Decisions taken on defaults (in the L2 page's questions table; say if you want otherwise)

- **A PR opened with no file named keeps `#/o/r/pull/N`.** The app writes the path form only once a file is named, by a link or a click. This avoids rewriting the address on every PR open and keeps today's `pull/12` and `pull/381?anchor=…` behaviour.
- **Q-RT-5:** a path matches a file's head path first, then its base path (renamed and deleted files).
- **History:** a click on a file pushes an entry, as today, so Back works; the rewrite after a cold link resolves uses replace, so Back does not land on the half-loaded link.
- **Address-bar rule ID:** LR-26 (the L2 pages use LR-10 to LR-25).

## Increments

### 1. Cold path link opens the right file after the manifest (riskiest: L2R-3)
- `src/lib/routing/route-adapter.ts` (new, the only browser-touching routing file): `readLocation()`, `publish(hash, {replace})` (push through `location.hash`, replace through `history.replaceState`), `onExternalChange(cb)` holding the write-loop guard that `lastWrittenHash` does today, and `restore(hash)` for the dirty-editor case (`:1116`).
- app-context:
  - `navigateToHash` uses `routing/route.parseHash` directly; the route's `file` ref travels into `_openPRInternal` in place of `fileIdx`.
  - Cold load: nothing is written before the manifest. When it arrives, `resolvePRFile` picks the index (head paths, then base paths). Found: select it and publish the path form with replace. `no-such-path`: open the first file, error "The linked file is not in this PR." `index-out-of-range`: today's error.
  - The warm branch (same PR already loaded, `:1072`) and demo mode resolve at once against the files they have.
  - `setSelectedPRFileIdxWithHash` publishes `buildRoute({type:"pr", file:{kind:"path", path}})` with push.
- `hash-router.ts` drops the `prFileIdx` compatibility layer and becomes a plain re-export of `routing/route.ts`.
- **Proof:** `e2e/pr-file-links.spec.ts`, desktop and mobile, with the files response held until the test releases it:
  - `f84_cold_path_link_opens_the_file_after_the_manifest`: the PR gained a file ahead of the linked one, and the linked file still opens;
  - `f84_path_with_spaces_and_percent_opens`;
  - `f84_clicking_a_file_writes_the_path_form_and_back_returns`;
  - `f84_missing_path_opens_the_pr_with_a_message`;
  - `f85_legacy_index_link_opens_and_shows_the_path_form`.
  - Component tests in `src/__tests__/pr-file-links.test.tsx`: `f84_no_hash_write_before_the_manifest`, `f84_resolve_replaces_rather_than_pushes`, `f84_renamed_file_matches_its_base_path`.
- Existing tests that assert the index form in the address bar follow the intended change (F-84, F-85), not a weaker check: `branch-links.spec.ts:96`, `pr-comment-navigation.spec.ts:81`, `branch-navigation.test.tsx:147`, and `review-links.test.ts:53-54` (moves to `buildRoute`). Their legacy `goto(".../files/N")` loads stay as F-85 coverage.

### 2. The other readers and builders go through the adapter
- `page.tsx:73-74` and `SignInBanner.tsx:35` call `readLocation()`.
- PRDetail: the jump-cancel listener uses `onExternalChange` plus a popstate subscription from the adapter, and compares parsed routes, not strings. The reference view's `pushState` and `history.back()` become adapter calls (`pushMarker`, `back`).
- `DiffViewer.tsx:375` builds the path form for an HTML link to another file in the PR.
- **Proof:** the existing comment-jump, reference-view, HTML link and sign-in suites stay green; `f84_html_review_link_href_uses_the_path_form` (unit, `review-links`).

### 3. LR-26: only the adapter touches the address bar
- `scripts/check-layout.mjs`: in `src/` outside tests, only `src/lib/routing/route-adapter.ts` may name `location.hash`, `"hashchange"`, `"popstate"` or `history.`.
- **Proof:** a layout-check test that a planted `location.hash` in another file fails with `LR-26 <path>`; `npm run ci` green.
- Docs: the L2 links page (route-adapter as built, LR-26, the defaults above marked decided), `docs/plan.md` WP-12 row.

## Relevant lessons

- `next build` rejects spreading a Set: use `Array.from`.
- E2E: open files with the shared helpers (`openMarkdownFile`, `openTreeFolder`); folders start collapsed since WP-11.
- The commit gate blocks failing tests: commit tests with their fix.
- The static-export Playwright run (`CI=1`) is the reliable one; the dev-server `npm run ci` stage flakes under load (M1-2).

## Verification

- Each increment: its named tests, then `npm run check`.
- End: `npm run ci` with its output pasted, plus the full Playwright suite on the static export (`CI=1`).
- Then an independent review (fresh Opus reviewer), fixes, re-review until PASS, and a PR. Merge only on your "merge".
- Manual check for you after merge: open a PR on mardoc.app, click its third file, copy the address. It ends in `/file/<that path>`. Open it in a new tab: the same file opens.
