L2 · Subsystem · Part of MarDoc architecture (L1)

Reviewers comment on the rendered document, and every review action goes through one GitHub adapter

Implements: the L1 PR review (PRDetail) card, as-is at c62d712. Two issues change it: #140 (number order, every page, jump to a number) and #139 (a checkmark for approved).

Folds in stories 001, 003, 010 (two), 011, 016, 028 and 039. Reading time: 4 minutes · Prerequisites: MarDoc architecture

01 · WhyReviewers answer a PR without leaving the rendered document

MarDoc exists to review Markdown and HTML in PRs; this area is that job. L1

Without it a reviewer reads raw diffs on github.com.

02 · ContractGitHub owns every review fact, and its list API does not sort by number

MarDoc keeps no copy of reviews, so the list must page GitHub and sort in the browser. Approval follows GitHub's rules (required reviewers, CODEOWNERS, dismissals), which only GraphQL reviewDecision reports. Both must stay cheap for hundreds of PRs.

05 · ProposedOrder and approval become pure functions

Proposals, not behaviour. Both put their logic in src/lib/pr-list.ts (new) and leave components to render.

#140 number order. The adapter pages pulls.list with sort: "created", because the endpoint has no sort by number (the loop in commentPages, github-api.ts:521, is the pattern). The first page shows at once; later pages load in the same abort-guarded load, up to 1000 PRs. The counts query runs per page of 100, so one failure clears at most 100 badges. sortByNumber(prs, "desc") then fixes the order whatever the API returns. filterPRs(prs, query) matches "123" or "#123" on number, else title. findByNumber(prs, n) backs a jump box; a miss calls the existing fetchPullRequest (github-api.ts:399).
#139 checkmark. The per-page counts query also asks for each PR's reviewDecision (APPROVED, CHANGES_REQUESTED, REVIEW_REQUIRED, or null). That applies GitHub's own rules, so a comment after an approval keeps the mark, as it does on github.com. approvalMark(decision) returns "approved", "changes" or none. The list row and the PR detail badge show a check only for "approved". The badge today shows the same check for "Changes Requested" (PRDetail.tsx:584); that changes to a different mark.

06 · JourneysTwo requests, hop by hop

Each hop names the part that acts.

Read each journey in order; with JavaScript off every scenario stays visible.

“I comment on a paragraph, a colleague replies, I resolve it”

  1. Diff views sends the selection and body to PR detail through onAddComment.
  2. PR detail queues a pending comment locally; on review submit it calls submitReviewBatched (github-api.ts:875).
  3. GitHub adapter posts with pulls.createReview; GitHub stores it.
  4. PR detail polls every 30 s and merges fresh comments with mergeFreshComments (PRDetail.tsx:135). A reply goes out as replyToReviewComment; Resolve calls resolveReviewThread (PRDetail.tsx:345).

“I type 12 and reach PR 12 (proposed, #140)”

  1. PR list passes the typed text to filterPRs.
  2. pr-list.ts returns matches in number order, or none.
  3. GitHub adapter runs fetchPullRequest only when the list has no match.
  4. PR state opens the PR with openPR.

08 · RulesLogic stays pure; GitHub stays behind the adapter

  • Pure in src/lib: comment-target.ts, comment-merge.ts, suggestion-body.ts, suggestion-extract.ts, and the proposed pr-list.ts. No I/O, no clock, no globals.
  • Adapter: github-api.ts is the only caller of GitHub for PRs and comments.
  • CI today: the layout check and no-DOM tsc cover only src/lib/auth/** and worker/src/domain/** (check-layout.mjs), not the PR helpers.
  • Proposed: pr-list.ts, comment-target.ts, comment-merge.ts and the suggestion helpers become entries in the shared pure-modules rule, LR-12 (Q-PR-3).

09 · ProofThree checks show it works; the full list goes in the slice plan

  • A fake-Octokit test: 250 PRs arrive as 250 rows in number order, the first page renders before the last arrives, and no counts query names more than 100 PRs.
  • A reviewDecision fixture recorded from a real GitHub response, including approve-then-comment, drives approvalMark. Hand-written review arrays would not show GitHub's rules.
  • filterPRs and findByNumber accept "12" and "#12"; a miss falls back to fetchPullRequest.

Keep green: per-file-comment-filter.test.tsx, comment-merge.test.ts, comment-pagination.test.ts. Test names cite F-n once the issues have rows (Q-PR-6). Status: planned.
