L1 · Architecture · GitHub sign-in, stage 1 · 2026-10-21

Sign in with GitHub in a pop-up; the token stays in memory for 8 hours

A reviewer clicks Sign in with GitHub, approves MarDoc on GitHub, and is back on the same page with a token that reaches only the repositories where MarDoc is installed. A small Worker on mardoc.app/api/auth/* does the one step a static page can't. The personal access token keeps working beside it. requirements.md

01 · WhyReviewers sign in instead of making a token

MarDoc's first step today is a token form most of its readers have never filled in, and the token it keeps is broad, long-lived and readable by document scripts. setup-github-pat.md SEC-01

Who benefits

New reviewers: product managers, designers and writers who have never made a token. Everyone gets a token limited to installed repositories that expires after 8 hours. GitHub docs

What improves

Connecting takes at most 2 clicks where MarDoc is installed (F-11). No token is stored (F-30). Expiry and reload cost one more click, and nothing on the page is lost (F-35).

Evidence

The owner's issue #146 and the L0 decision D-1. "About 2 clicks" is the owner's target, not a measurement. SP-1 proved the route and installation scoping on the live zone. L0 SP-1

Covers stage 1: Settings sign-in, the Worker, the in-memory session, expiry, installs and the PAT fallback. Out of scope: silent refresh (stage 2, see Concerns), VS Code extension sign-in, the SEC-01 fix and any hosting move. intent.md

02 · The problemA token must reach one tab without touching storage or a URL

GitHub issues the token only to a server holding the App's secret, but the tab that needs it is a static page that also runs untrusted documents. ADR 0001

A reviewer's GitHub account authorises the MarDoc GitHub App. The App has installations on chosen repositories; in an organisation an org owner approves them. GitHub then issues a user access token that reaches a repository only when an installation covers it, and it expires after 8 hours. Issuing it needs the App's client secret, and GitHub's token endpoint sends no CORS headers, so a page in the browser cannot finish the exchange. community #15752 SP-1 criterion 4

Three things make it hard. The token has to cross from a server-side step into one tab, and the tab must be sure the token answers the sign-in it started. Storage and URLs are off limits, because a rendered document's script runs as mardoc.app and would read them (S-25). The token dies after 8 hours or on reload, and the reviewer must not lose their place (S-15). intent.md RK-1

Under the hood: terms

Sign-in token: a GitHub App user access token, held in memory. Attempt: one click of Sign in, with a pop-up and a one-time value (the nonce). Sign-in result: the message the callback page posts back. Installation: GitHub's record of which repositories the App may reach. Sign-in marker: a non-secret localStorage key that says this browser used sign-in last. design.md

Key idea: the tab never navigates. The sign-in runs in a pop-up, and only its last page talks back to the tab, so the reviewer's route, document and edits stay put.

03 · The piecesTwo new parts and two changed ones; documents still go straight to GitHub

The Auth Worker and the GitHub App are new. The Settings screen and the app's auth state change. The GitHub client, storage and Pages stay almost as they are. design.md

The app runs in the reviewer's browser, served by GitHub Pages. The Auth Worker runs on Cloudflare's edge for /api/auth/* only, and GitHub is external. No other server exists, and documents never pass through the Worker. Pages serves every other path, as SP-1 showed with the route in place. SP-1 criterion 2

Settings screen ◐ Partial

Where a reviewer signs in, sees who they are signed in as, installs MarDoc on more repositories, or falls back to a token.

Owns

Whether the token form is open; nothing persistent. Exists: the PAT form, Connect and Disconnect. To build: Sign in first, "Signed in with GitHub as login", the install link, the "installed nowhere" message, failure messages with the token option, PAT steps matching the guide (F-10, F-13, F-41, F-44, F-51, F-54).

Interfaces

Calls startSignIn() inside the click handler, so the pop-up passes pop-up blockers. Calls connectPat(token) and disconnect(). Links github.com/apps/<slug>/installations/new in a new tab. Its banner above the main pane shows the expiring, expired and reload prompts (F-37).

Boundary

Does not hold the token or talk to the Worker; auth state does. Not shown in the VS Code embed (F-15). When MarDoc is inside another page's frame outside embed mode, replaces every Sign in and Sign in again button with an "Open MarDoc in a new tab" link (target="_blank", rel="noopener noreferrer") and keeps the token option (F-19). Stops saying "there is no server" (F-72, Q-10).

Failure

Shows each failure code as a message, always with "Use a personal access token" and the guide link. Signing in leaves a saved PAT in place, unused until the sign-in session ends; the signed-in view says it will be used after Disconnect and offers to remove it (F-53, F-55).

Exists: SettingsPanel.tsx:97-110, 196-253 at 2b79817. Design: design.md § Settings screen

App auth state ◐ Partial

Holds the tab's one credential (a PAT, an embed token or a sign-in token), runs a sign-in attempt, and watches expiry.

Owns

The credential, with login and expiry for a sign-in token; the session status (signed-out, signing-in, checking-user, signed-in, expiring, expired, sign-in-again; a failed attempt returns to the status before it with an error); the current attempt's pop-up, nonce and 10-minute deadline (F-28). Exists: githubToken and setGithubToken. To build: everything else.

Interfaces

Opens the pop-up at /api/auth/login?n=<nonce> and fetches /api/auth/health. Accepts a message only from the app origin, from its own pop-up, with its nonce (I-11). Calls initOctokit, resetGitHubSession and GET /user. Starts nothing when framed (window.top !== window.self, or reading top throws): no pop-up, no health check, no session event, and its message listener ignores results; it exposes the same check as isFramed for Settings and the banner (F-19). Exposes a session key (pat, embed, sign-in:login), never the token, so a same-login swap re-runs no navigation. Writes only the sign-in marker.

Boundary

Does not store a sign-in token anywhere (I-10). Does not render UI or decide repository access. A saved PAT wins at start-up, and an embed token wins over both.

Failure

A blocked pop-up, failed health check, error result or timeout ends the attempt as failed(code), leaving any existing credential alone. Expiry or a 401 gives expired: requests stop, the page stays, and Sign in again is offered ("Open MarDoc in a new tab" instead when framed, F-19).

Exists: app-context.tsx:144-146, 286-331 at 2b79817. Design: design.md § Session status

Auth Worker ○ To build

The only server-side step: swaps the sign-in code for a token, hands it to the tab that asked, and can revoke it.

Owns

No durable state (F-26). One HttpOnly cookie per attempt on /api/auth, named by the attempt's nonce, holding state and the PKCE verifier; 10 minutes†, cleared at the callback (F-28). The client secret, as a Worker secret only (C-13).

Interfaces

GET /health, GET /login?n= (302 to GitHub with S256), GET /callback (a page that posts the result, as escaped JSON, to window.opener at https://mardoc.app, then closes; I-17), POST /revoke (same origin only). Every response no-store, no CORS headers.

Boundary

Does not return, store or log a refresh token (I-13), and has no /refresh (F-25). Does not log at all (I-16). Never sees documents.

Failure

A GitHub error becomes its code; a GitHub outage becomes exchange_failed; a bad state becomes state_mismatch with no exchange (I-12). If the Worker is down or unrouted, the tab's health check catches it within 5 s† and offers the PAT. Health answers 503 {"ok":false}, naming neither, when CLIENT_ID or CLIENT_SECRET is empty; the tab treats that like an outage and shows the F-51 unavailable message.

Design: design.md § Worker routes. Evidence: the disposable SP-1 Worker proved routing and installation scoping (owner-reported; Results to be pasted); it is not product code. SP-1

MarDoc GitHub App ○ To build

GitHub's record of what MarDoc may do and where: its permissions, its callback and its installations.

Owns

Client ID and secret; permissions Contents read and write, Pull requests read and write, Metadata read (NF-10, Q-19); callback https://mardoc.app/api/auth/callback; expiring user tokens; "Request user authorization during installation" off, so installing doesn't land on the callback (A-11); installations.

Interfaces

The consent screen at github.com/login/oauth/authorize. The install page github.com/apps/<slug>/installations/new, where an org member who is not an owner can only request an install and GitHub notifies the org owners.

Boundary

Runs no code. MarDoc uses no installation tokens or webhooks in stage 1. Only the owner registers or changes it (C-14); the name and slug are public (Q-19).

Failure

A suspended App or a revoked authorisation makes sign-in tokens fail with 401, so users see Sign in again, then a sign-in error with the PAT option. A leaked secret is rotated by the runbook (NF-21, SP-2).

Production App not registered; SP-1 used a test App. design.md § GitHub App GitHub docs

04 · JourneysSign-in, an org request, expiry and an outage all keep the reviewer's place

Each journey ends with the reviewer on the page they started on: signed in, waiting for an install, signing in again, or using a token. design.md

Read each journey in order; with JavaScript off every scenario stays visible.

“I sign in for the first time”

  1. Settings screen receives the click on Sign in with GitHub and calls startSignIn() on auth state (F-10).
  2. App auth state makes a nonce from 16 random bytes, opens the pop-up at /api/auth/login?n=<nonce>, and at the same moment fetches /api/auth/health.
  3. Auth Worker (login) creates state and a PKCE verifier, sets the attempt cookie, and redirects the pop-up to GitHub with an S256 challenge (F-21).
  4. MarDoc GitHub App's consent screen asks the reviewer to authorise MarDoc. They approve, and GitHub sends the pop-up to /api/auth/callback?code&state.
  5. Auth Worker (callback) checks state against its cookie (I-12), exchanges code, verifier and secret with GitHub, drops the refresh token (I-13), and returns a page that posts the token and expiresIn to the opener at https://mardoc.app.
  6. App auth state accepts the message only from its pop-up with its nonce (I-11), calls initOctokit(token) and GET /user, records login and expiry in memory, and writes the sign-in marker. The route and open document are untouched (F-12).
  7. Settings screen shows "Signed in with GitHub as login" (F-13); the repository picker lists installed repositories (F-40).

“I sign in, but my org hasn't installed MarDoc”

  1. App auth state completes sign-in as in the first journey.
  2. GitHub client lists the reviewer's installations; the org's repos are not there, and opening a link to one gets 404 (F-40).
  3. Settings screen's message in the main pane says MarDoc may not be installed on owner/repo, with the install link and the token option (F-42). With no installation at all, the repository list says so too (F-44).
  4. MarDoc GitHub App's install page: the reviewer picks the org and, not being an owner, sends a request. GitHub notifies the org owners, and one approves.
  5. GitHub client lists installations again with the same token when the reviewer clicks Refresh; the repo appears with no new sign-in (F-43, SP-1 criterion 5).

“My token expires mid-review”

  1. App auth state reaches 10 minutes† before expiry and shows a banner with Sign in again (Q-26).
  2. GitHub client is reset at expiry; its request hook refuses any request with the old token (I-15). A 401 before then has the same effect (F-34). The page, route and unsaved edits stay.
  3. Auth Worker runs the same login and callback when the reviewer clicks Sign in again. GitHub has recorded the authorisation, so the pop-up usually closes without a consent screen (inferred; SP-3 measures it).
  4. App auth state calls GET /user. Same login: it only swaps the token; the session key doesn't change, so the open file is not re-fetched and every edit stays (F-35). A different login resets repository state, as connecting does today (F-36).

“Sign-in is down, so I use a token”

  1. App auth state opens the pop-up and fetches /api/auth/health.
  2. Auth Worker is down or unrouted: health returns a Cloudflare 5xx, a GitHub Pages 404, the Worker's own 503 {"ok":false} (CLIENT_ID or CLIENT_SECRET empty), or nothing within 5 s† (F-51).
  3. App auth state closes the pop-up and records failed(worker_unavailable); any existing credential is untouched.
  4. Settings screen says sign-in is unavailable, opens the token form and links the PAT guide (F-51, F-71).
  5. GitHub client starts with the pasted PAT, which is saved and restored exactly as today (F-50).

“I reloaded the tab”

  1. localStorage holds no token, only the sign-in marker (Q-20).
  2. App auth state finds no PAT, sees the marker, sets sign-in-again and keeps the hash route instead of loading demo data (F-32).
  3. Settings screen's banner says "Sign in again to open path" and offers Sign in again or "Continue without signing in", which removes the marker (F-37, F-38). Unsaved edits from before the reload survive only where drafts already do: Markdown files in repositories, not HTML files or unsent PR comments.

05 · FailuresEvery sign-in failure leaves the current credential alone and offers a token

A failed attempt never signs the reviewer out or clears a saved PAT; Settings names what failed and shows the token option. design.md § result codes

Read each failure below; JavaScript adds selection and playback.

My browser blocks the pop-up

Reacts: App auth state. You see: "Allow pop-ups for mardoc.app, or use a token." Recovery: allow pop-ups and click again, or paste a PAT.

  1. Settings screen calls startSignIn() from the click.
  2. App auth state gets null from window.open and records failed(popup_blocked).

MarDoc is open inside another page

Reacts: Settings screen and App auth state. You see: "Open MarDoc in a new tab" in place of Sign in; the token option stays. Recovery: open MarDoc in its own tab and sign in there, or paste a PAT. Embed mode is unaffected (F-19, design.md § Security and privacy, T-34).

  1. App auth state sees window.top !== window.self, or that reading top throws, and starts nothing: no pop-up, no health check.
  2. Settings screen and the banner read isFramed and show the new-tab link instead of Sign in and Sign in again (F-19).

I cancel on GitHub

Reacts: Auth Worker, then auth state. You see: "Sign-in was cancelled." Recovery: click Sign in again or use a token.

  1. MarDoc GitHub App's consent screen redirects with error=access_denied.
  2. Auth Worker posts a result with only that code.
  3. App auth state records failed(access_denied).

Another window posts a fake result

Reacts: App auth state. You see: nothing; the attempt continues. Limit: I-11 stops a fake result from being accepted; it does not stop a same-origin document script from reading the real token out of the tab's memory (RK-1, see Concerns).

  1. Rendered HTML iframes: a document script posts a correctly shaped result, with an attacker's token, to the tab.
  2. App auth state sees that event.source is not its pop-up, or that the nonce differs, and ignores it (F-14).

The callback doesn't match the sign-in

Reacts: Auth Worker. You see: "Sign-in could not be verified. Check that cookies are allowed for mardoc.app, then try again", with the token option. Recovery: allow cookies and try again, or use a token (F-28).

  1. Auth Worker finds the attempt cookie missing or its state different and returns state_mismatch without contacting GitHub (I-12). The nonce travels inside state, so the tab can still be told.
  2. App auth state records failed(state_mismatch); if even the nonce is unusable, it reports a closed window after 1 s†, also with the token option (F-52).

GitHub doesn't answer the exchange

Reacts: Auth Worker. You see: "GitHub did not answer. Try again." Recovery: retry later or use a token, which also needs GitHub.

  1. GitHub times out or returns 5xx on login/oauth/access_token.
  2. Auth Worker posts exchange_failed.
  3. App auth state records failed(exchange_failed).

MarDoc isn't installed on the repo I opened

Reacts: GitHub client and Settings. You see: "MarDoc may not be installed on owner/repo", with the install link and the token option. Recovery: the org install journey.

  1. GitHub returns 404 for a repository outside the installation.
  2. GitHub client rethrows the 404.
  3. Settings screen shows the message (F-42).

06 · ConcernsStage 1 narrows token exposure but doesn't close it; refresh waits for SEC-01

A document script can still take the in-memory token, so stage 1 accepts that exposure only because the token is 8-hour and installation-scoped, and it ships no refresh route. risks.md

RiskWhat it means hereHow stage 1 bounds it
SEC-01 / RK-1Three viewers run document scripts as mardoc.app. They can read the sign-in token from the tab's memory or listen for the result message.No stored token (F-30), so nothing survives the tab. The token expires in 8 hours and reaches only installed repos. There is no refresh route (F-25). SEC-01 is owned by Joe Barnett, due 2026-11-17 (Q-4).
RK-2Cloudflare runs the Worker, so a compromised deploy or account could capture tokens.The Worker logs and stores nothing (I-16, F-26). Only the owner deploys (C-14). The README, data-and-security.md and capabilities.md say so (F-70).
RK-3The init listener accepts a token from any window, so a document could swap the signed-in token for another.F-16 makes the init checks a stage 1 prerequisite. The owner accepted that default (Q-27, 2026-10-27), so stage 1 ships only with the init checks.
Under the hood: login CSRF and token leakage

The state cookie stops a forged callback from being exchanged (I-12). The nonce, checked with event.source, stops a result from another attempt or window being accepted (I-11). The callback page's Content Security Policy allows only its own nonce script and forbids framing. The token never appears in a URL, a Location header, history or storage (NF-11). design.md § Security

Stage 2 note. Silent refresh adds /api/auth/refresh and a stored refresh token so users stay signed in across 8 hours and reloads. It is out of scope here. It waits for the SEC-01 fix and its own gate: no injected script can read app storage or get a token from the refresh route, and a cross-site fetch to it is refused. requirements.md § Stage 2 note

Operating it. Joe Barnett operates the Worker, deploys it with wrangler from a tagged commit, and holds the client secret only in Worker secrets (Q-7). It runs on the Workers Free plan; a usage notification at 50% of the daily limit warns of abuse. The secret is rotated yearly and on suspected compromise (NF-21, SP-2). If the Worker breaks while the operator is away, sign-in stops and the PAT keeps working; there is no second operator (Q-9). L0 operating commitment

What must happen before stage 1 ships. You accept this design and decide Q-19 (the App's public name); SP-3 shows the pop-up hand-off works in five browsers with the real callback page; you register the production App and deploy the Worker; the build-prerequisites work package lands; the stage 1 gate tests pass (no token in storage, no refresh route); and Q-27 is decided. plan.md Gate 0

Key idea: stage 1's safety comes from what it leaves out: no storage, no refresh route, no logs.
