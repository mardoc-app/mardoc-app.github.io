Replace the pasted PAT with “Sign in with GitHub”, using one small Worker on mardoc.app

Before a new reviewer can read anything, MarDoc asks them to make and paste a personal access token. A GitHub App sign-in, with its code exchange in a Cloudflare Worker on mardoc.app/api/auth/*, swaps that for a sign-in button, per-repo access and 8-hour tokens, with no hosting change. GitHub docs

Proposal for issue #146, based on the code at commit 2590742 · Decision needed by 2026-10-27 (default, Q-6) · Decision and gate status: plan.md D-1, ADR 0001 · Reading time: 5 minutes

01 · WhyReviewers sign in instead of making a token

MarDoc is for product managers, designers and writers, and its first step today is a token form most of them have never filled in. README setup-github-pat.md

Who benefits

New reviewers who have never made a PAT, and users in orgs that block PATs but allow approved GitHub Apps. The org case is a hypothesis from #146 and hasn't been checked with any org.

What improves

The user clicks Sign in with GitHub and consents. The first time, MarDoc also has to be installed on their repos, and on org repos that may need an org owner's approval. Tokens expire after 8 hours. In the first release the user signs in again when that happens; silent refresh follows once SEC-01 is fixed. MarDoc already supports fine-grained PATs, which are per-repo and expiring, but users still have to make and paste them by hand. GitHub docs

Evidence

An owner-stated need (2026-10-20) and issue #146. Its “about 2 clicks” is a target, not a measurement, and there is no data on how many users drop off at the PAT step. #146

02 · SituationThe app and the Cloudflare zone exist; only the code-for-token exchange is missing

Today the user pastes a PAT in Settings. MarDoc stores it in localStorage.mardoc_github_token and hands it to initOctokit, and a 401 response asks for a new token. app-context.tsx:91 github-api.ts:43 rate-limit.ts:139

The site is a static export on GitHub Pages, and Cloudflare already proxies mardoc.app: its nameservers are Cloudflare's, and responses carry cf-ray and x-github-request-id (checked 2026-10-20). Q-5

What's missing: GitHub sends the sign-in code back only to the app's registered callback URL. The swap of code for token requires the client secret GitHub docs. GitHub's guidance lets a single-page app ship that secret with PKCE GitHub docs, but users report that the token endpoint sends no CORS headers, and GitHub staff said in 2025 that CORS support was still to come community #15752. A browser page can't make the call, so the swap needs a server-side step. #146

Reused: the Cloudflare zone, setGithubToken and initOctokit, the 401 path, and the PAT flow as a fallback. The e2e specs that seed the token in localStorage keep working. #146

Existing risk that sign-in shrinks but doesn't remove: three viewers render HTML in iframes with allow-scripts allow-same-origin, so document scripts run as mardoc.app. Today such a script can read the stored PAT, which often has broad scope and no expiry. With sign-in, a script could still capture the in-memory access token, but that token is limited to installed repos and expires in 8 hours. A refresh route would let the script keep minting new tokens, so refresh waits for the SEC-01 fix. HtmlViewer.tsx:358 DiffViewer.tsx:1120 RepositoryReference.tsx:53 SEC-01 RK-1 Q-4

03 · The piecesOne Worker route handles sign-in; documents still go straight from the browser to GitHub

The user signs in and consents on GitHub, and GitHub redirects back to mardoc.app/api/auth/callback. Cloudflare routes that path to the Auth Worker. The Worker checks the sign-in request's state, swaps the code for tokens with the client secret, and returns the access token to the app. Once SEC-01 is fixed, it also handles refreshes. Every other path still goes to GitHub Pages.

This puts the callback in the Worker rather than on a static /auth/callback page as #146 sketched. The secret-holding step and the callback share one origin and one deploy. Token storage, the hand-off to the app and the CSRF details belong to the L1 and L2 design. #146 Q-3, Q-5

What changes for privacy: GitHub tokens now pass through a Worker that Joe Barnett operates, deployed with wrangler, with the secret held only in Cloudflare, so Cloudflare becomes a third party in the credential path (RK-2). The Worker stores nothing. If it is down, sign-in fails, and the PAT option keeps working. The README, data-and-security.md and capabilities.md must say so. Q-7

04 · DecisionOne direction to approve, two release stages, and three proofs that can reverse it

1 / The route works on the live zone

This is the spike, time-boxed to 2 days. On a test GitHub App, a sign-in round trip through /api/auth/callback returns the user's login, other paths still serve Pages content (x-github-request-id present), and a health probe on /api/auth/health reports failure if the route stops reaching the Worker, for example after the proxy is switched off. If it fails: move the Worker to auth.mardoc.app.

2 / Access matches the installation

In the same spike, a user token reaches a repo where the test app is installed and gets 404 on one where it isn't. A non-owner org member's install request is observed end to end. If it fails: revisit the classic OAuth App with an ADR. If org-owner approval makes sign-in slower than a PAT: Settings offers both paths side by side for org repos, and says that installing needs an owner while a fine-grained PAT may need org approval too. Sign-in becomes the default only where the app is already installed. setup-github-pat.md

3 / Each stage is safe to ship

Release gates. Stage 1: after sign-in, browser tests find no GitHub token in localStorage or sessionStorage, and the Worker has no refresh route. Stage 2: with SEC-01 fixed, browser tests show that no script injected through rendered HTML, Markdown or a PR description can read app storage or get a token from /api/auth/refresh, and a cross-site fetch to that route is refused. If a gate fails: that stage doesn't ship.
