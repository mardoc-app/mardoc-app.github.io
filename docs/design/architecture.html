MarDoc is a static browser app that reads and reviews GitHub documents directly from the browser

This page describes what the code does at 2b94d90, checked on 2026-10-20. It is a baseline for adoption: accurate, not endorsed, and it states no plans.

01 · WhyReviewers read GitHub documents as documents, not as raw diffs

MarDoc gives product managers, designers, writers and engineers a rendered reading and review surface for Markdown and HTML in GitHub repositories. README.md:3-7

Who benefits

Reviewers of version-controlled documents who don't want raw diffs as their main reading surface.

What improves

Rendered Markdown and HTML, comments on selected passages, and Markdown edits that become a pull request.

Evidence

The product statement in the README; this baseline makes no new value claim. README.md:5-9

In scope: the browser app at 2b94d90 and its contacts with GitHub, the VS Code extension and the optional AI endpoint. Out of scope: the extension's own code (mardoc-vscode) and GitHub itself. capabilities.md

02 · The problemDocuments, PRs and comments live in GitHub, and the app has only a browser

Everything the reviewer works on is held by GitHub; MarDoc runs as static files with no backend, so the browser must hold the credential and do all the work. architecture.md:3

A reviewer opens a document from a repository branch or from a pull request. A pull request has a base and a head revision for each changed file; review comments anchor to line ranges in a file and are submitted as a review. A reviewer can also open a local file: in the browser with a file picker for .md, .mdx, .markdown, .html and .htm (Sidebar.tsx:306-318, app-context.tsx:659-673), or through the VS Code extension. capabilities.md

Constraints: the app is a static export with no API routes or database; GitHub requests go straight from the browser with the user's token; rendered HTML documents can contain scripts and load external assets. next.config.js:4 data-and-security.md:5-9

Under the hood: terms

Demo mode: no token; mock files and PRs. Embed mode: loaded with ?embed=true inside the VS Code webview. Revision: the commit SHA a file was read at. Pending comment: a line-anchored comment queued in the browser before the review is submitted (PRDetail.tsx:161-163). app-context.tsx:98-104

Key idea: the credential and every document pass through the browser tab, so whatever runs in that tab shares them. data-and-security.md:29-35

03 · The piecesOne static shell, several views, and a single GitHub client in the browser

Apart from the static files, every MarDoc part runs in the browser tab; GitHub, the extension and the AI endpoint are outside. architecture.md:5-9

No MarDoc part runs on a server. The static site is deployed to GitHub Pages; Cloudflare in front of it is an observation from response headers on 2026-10-20, not something the code shows. The shell, views, storage, token state, GitHub client and embed listener run in the tab; GitHub, the VS Code extension and the optional AI endpoint are external. deploy.yml:32-44 public/CNAME

All components are described below.

Static site ● exists

Serves the exported app files; no server code runs for MarDoc.

Owns

The out/ export of the Next.js app, deployed to GitHub Pages for the custom domain mardoc.app. Observed, not derivable from code: response headers on 2026-10-20 carried server: cloudflare, cf-ray and x-github-request-id, so Cloudflare sits in front of Pages.

Interfaces

Browser → HTTPS GET for HTML, JS and CSS. Every route is the same shell; navigation lives in the URL hash.

Boundary

Does not run API routes, store data or see documents; the browser does all of that.

Failure

Site unreachable: the app does not load. After load, the only fetch from the static site is the lazily imported Mermaid chunk, so a later outage breaks the first Mermaid diagram only mermaid.ts:61-68.

Source: next.config.js:4 deploy.yml:32-44 public/CNAME

App shell and state ● exists

Holds the session: which repo, branch, file or PR is open, and which view shows it.

Owns

The current repo and branch, the selected file or PR, loaded PR files with their per-file load state, comments, and the load guards. Token state lives in the same AppProvider and is described on the connection page.

Interfaces

Hash routes in and out (parseHash, hashchange); calls the GitHub client; picks the view: editor, HTML viewer, PR diff (PRDetail) or the create-review-PR view (PRReview).

Boundary

Does not call GitHub directly; the GitHub client does. Does not render documents; the views do. Shows mock files and PRs while token state reports demo mode.

Failure

A failed load sets an error from formatApiError; the target view is already selected and shows no content (a failed tree load also empties the file list, app-context.tsx:534). Stale results are dropped by generation guards. app-context.tsx:541-543 app-context.tsx:585-605 app-context.tsx:680-698

Source: app-context.tsx:97 app-context.tsx:508-536 app-context.tsx:703-715 app-context.tsx:731-783 page.tsx:285-338 · Detail: links and routing, repository browsing, resilience

Under the hood: load guards and on-demand lists

Opening a repo activates the revision and tree only; branch and PR lists load on demand, and PR-list loading is guarded and abortable. docs/architecture.md:39-45 says otherwise (X-10, X-12). app-context.tsx:451-465

Token state (AppProvider)

The GitHub token and demo mode, held in the same AppProvider as the app shell: localStorage for a pasted PAT, memory only for a token from the VS Code extension. Defined in GitHub connection, as-is.

GitHub client (Octokit + retry)

One module-level Octokit client with retries, a recorded rate-limit pause and session caches. Defined in GitHub connection, as-is.

Markdown editor ● exists

Shows a repo or local Markdown file as a rich document and turns edits into a commit or PR.

Owns

The TipTap document for the open file; code-view text while code view is on.

Interfaces

Markdown → HTML with Showdown, HTML → Markdown with Turndown; creates review PRs and commits through the GitHub client; in embed mode posts file:save to the parent.

Boundary

Is not a lossless source editor; conversion is a normalising pipeline (docs/architecture.md:49). Does not open HTML files; the HTML viewers do.

Failure

Draft writes fail silently when storage is unavailable; a failed PR creation shows an error.

Source: Editor.tsx:4-20 Editor.tsx:185-198 Editor.tsx:1101 Editor.tsx:1236 Editor.tsx:1293 · Detail: editing

PR review (PRDetail) ● exists

Shows a PR as rendered documents with base/head differences and collects review comments.

Owns

The pending queue of line-anchored comments, held in component state (PRDetail.tsx:161-195); the comment refresh timer.

Interfaces

Reads files and comments through the GitHub client. A comment with selected text and a line range is queued; a comment without one is posted to GitHub at once (PRDetail.tsx:199-217). Submits the queue with submitReviewBatched; refreshes comments every 30 s while visible and after writes (background-refresh.ts:17); optional draft polishing through the AI feedback endpoint.

Boundary

Does not persist the pending queue: it is component state, lost on reload (data-and-security.md:20). Does not render HTML itself; the HTML viewers do. The create-review-PR view is PRReview, a different component.

Failure

On a 422 line-resolution error, comments are posted one by one; a comment GitHub cannot anchor becomes a PR conversation comment with document context, and the reviewer gets a notice (review-fallback.ts:54-62, PRDetail.tsx:296-297). The review itself is then submitted only if the event is not COMMENT or a body was given (github-api.ts:827). If a post fails midway, posted comments leave the queue and the rest stay pending (review-fallback.ts:63-66).

Source: PRDetail.tsx:277 github-api.ts:797-841 review-fallback.ts:4-13 · Detail: PR review, HTML comments

Browser storage ● exists

Keeps settings, the last repo and Markdown drafts between visits.

Owns

localStorage keys written or read by the app: the token, mardoc_current_repo, mardoc_user_repos, mardoc:draft:v1:*, theme, mardoc_wide_format, mardoc:image-folder:*, the feedback-AI settings, and mardoc_profile (read only).

Interfaces

Read and written through safe-storage.ts, except drafts (own guard in draft-store.ts:28-35) and image-folder keys (own guard in image-path-config.ts:48-55). All three swallow errors.

Boundary

Does not encrypt anything and does not back up drafts; new and local files are not drafted.

Failure

Storage blocked or full: reads return null and writes are dropped without a message.

Holds the repositories, files, PRs, reviews and comments MarDoc reads and writes.

Owns

AI feedback endpoint ◇ external

Rewrites a review-comment draft when the user turns the feature on.

Owns

Nothing in MarDoc; the endpoint and model are user settings.

Interfaces

One POST per request with the draft only, a 30 s timeout (feedback-ai.ts:75), no cookies, no referrer and no redirects; the API key is held in memory.

Boundary

Is off by default and never receives repository or thread context.

Failure

Timeout or error: the draft stays as written.

Hosts the app in a webview for local files and supplies a GitHub token when it has one.

Owns

Local file access, the webview, and its own GitHub sign-in.

04 · JourneysEvery journey starts in the shell and reaches GitHub through one client

The four main paths at 2b94d90: demo, opening a document, reviewing a PR, and the VS Code embed. app-context.tsx

Read each journey in order; with JavaScript off every scenario stays visible.

“I open mardoc.app for the first time”

  1. Static site returns the exported shell for any path. next.config.js:4
  2. App shell shows mock files and mock PRs while token state reports demo mode, which starts on. app-context.tsx:145-154
  3. Token state finds no saved token, so demo mode stays on. app-context.tsx:309-318
  4. Markdown editor shows the chosen sample from mock data; no GitHub call is made. app-context.tsx:589-591

“I open a document on a branch”

  1. App shell parses the hash route, saves mardoc_current_repo and resolves the branch to a commit SHA. app-context.tsx:581-597
  2. GitHub client loads the tree in the background and the file content at that SHA. app-context.tsx:597-603
  3. Markdown editor converts the Markdown with Showdown (Editor.tsx:185-198), then compares any saved draft with the Turndown round-trip of the loaded text: a draft that differs gets a restore prompt, and an equal one is deleted. Nothing is restored automatically. draft-store.ts:143-155 Editor.tsx:841-860

“I review a pull request and submit comments”

  1. App shell loads comments and the paginated file manifest together. app-context.tsx:676-700
  2. GitHub client pages through pulls.listFiles, keeps previous_filename for renames, and loads only the selected document's base and head. github-api.ts:393-417
  3. PR review shows the rendered diff and queues line-anchored comments; a comment without a selection posts at once. PRDetail.tsx:161-217
  4. GitHub client submits one review. On a 422 line-resolution error it posts comments one by one, turning unanchorable ones into PR conversation comments, then submits the review only if the event is not COMMENT or a body was given. github-api.ts:797-841
  5. PR review refreshes comments after the write and every 30 s while the tab is visible. background-refresh.ts:17

“I open a local Markdown file in VS Code”

  1. VS Code extension loads ${appBase}/?embed=true in a webview frame; appBase defaults to https://mardoc.app and is overridable by mardoc.appUrl (mardoc-vscode src/extension.ts:145, 203, 212-224 at 41088d5).
  2. App shell posts ready to the parent with target *. app-context.tsx:370-373
  3. Embed init listener receives init, posted by the webview wrapper script (mardoc-vscode src/extension.ts:261), and applies the token, repo and file. app-context.tsx:353-361
  4. Token state keeps the extension's token in memory only; it is not written to localStorage. The extension sends a token only when a VS Code GitHub session already exists (mardoc-vscode src/extension.ts:111). app-context.tsx:327-331
  5. Markdown editor shows the local file; saving posts file:save with the Markdown to the parent. Editor.tsx:1293

05 · FailuresErrors become messages; the session and token are untouched

For 5xx, 408 and network errors the GitHub client makes 3 attempts (2 retries) with about 0.5 s then 1 s backoff, ±25% github-api.ts:58-78. On a rate limit it records a pause and rethrows; only PR comment refresh checks it (PRDetail.tsx:133); other calls still go out and fail with the rate-limit message. No failure clears the token or the Octokit client.

Read each failure below; JavaScript adds selection and playback.

GitHub is rate-limiting or failing

Reacts: GitHub client. You see: a short wait for 5xx, or “GitHub rate limit reached. Resets in ~N minutes.” rate-limit.ts:149-160

  1. GitHub client makes 3 attempts (2 retries) with about 0.5 s then 1 s backoff, ±25% github-api.ts:58-78 for 5xx, 408 and network errors.
  2. GitHub client records a pause until the reset time (60 s if none is given) and rethrows; a successful response with zero remaining quota also records a pause (rate-limit.ts:71-82); only PR comment refresh checks it (PRDetail.tsx:133). rate-limit.ts:23-38
  3. PR review skips every comment refresh (the 30 s timer, tab-visibility and post-write refreshes) while the pause lasts. PRDetail.tsx:133, 145-156

GitHub rejects the token

Reacts: the calling view, through formatApiError. You see: “your GitHub token is invalid or expired. Open Settings to re-authenticate.” The token stays saved until the user disconnects. rate-limit.ts:137-152

  1. GitHub client returns the 401 without retrying, because a 401 is not a transient error. github-api.ts:73 rate-limit.ts:111-128
  2. App shell (the same AppProvider as token state), as the caller for loads, shows the message from formatApiError; nothing clears the token. app-context.tsx:533-534 rate-limit.ts:149-152

The browser blocks or fills localStorage

Reacts: Browser storage. You see: nothing at the time; the token, last repo and drafts are not there next visit. safe-storage.ts:6-28

  1. Browser storage catches the error, returns null on read and drops the write. safe-storage.ts:6-28

The repo has more than 100 PRs in the selected state

Reacts: GitHub client. You see: only the 100 most recently updated PRs. No doc mentions this limit (X-9). github-api.ts:296-304

  1. GitHub client requests one page of 100 PRs sorted by last update; it does not paginate the PR list. File manifests and comments do paginate. github-api.ts:296-304

The app is embedded but no init or image reply arrives

Reacts: Embed init listener. You see: the demo content, images that fail after 5 s, and reloads that do nothing. embed-image-bridge.ts:68-93

  1. Embed init listener waits for init; without it the shell stays in demo mode. app-context.tsx:145
  2. Embed init listener rejects image requests after 5 s and sends reload requests that get no answer. embed-reload.ts:40-44

Key idea: no failure clears the session by itself; recovery is a retry, a wait for the rate-limit reset, or the user acting in Settings. rate-limit.ts:149

Trade-offs: static hosting with no backend puts the credential and the work in the browser

The docs state the constraint and its costs; this baseline restates them. architecture.md:3

The project docs describe a browser-only app served as static files, with no application backend receiving content or authenticating users. They list the costs: the PAT is kept in browser localStorage and rendered documents can make their own network requests. README.md:9 data-and-security.md:5-9
