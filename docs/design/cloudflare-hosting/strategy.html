Serve mardoc.app's files from Cloudflare, keep sign-in in its own Worker, and keep GitHub Pages as the way back

Cloudflare already handles every mardoc.app request. A Worker with static assets and no code can serve the site's files and send the response headers GitHub Pages can't. Sign-in stays in the separate Auth Worker the L1 designed. The owner deploys both Workers by hand, and no pipeline holds a Cloudflare token. Each switch is a route held only in the Cloudflare dashboard, so going back is one deleted route that no deploy re-creates. Cloudflare docs sign-in L1

01 · WhyMarDoc gets its own response headers and a staging site, at no cost and with no new party

GitHub Pages lets a site set no response headers. Cloudflare's static assets read a _headers file, so MarDoc can send a Content-Security-Policy and other security headers. Headers are defence in depth; they don't close SEC-01 (rendered-content isolation) by themselves. Details are kept privately. Cloudflare docs SEC-01

Who benefits

Reviewers, because a policy adds defence in depth for rendered content. The owner, because a staging hostname with no users can test each release before it reaches mardoc.app.

What improves

Headers such as Content-Security-Policy, X-Content-Type-Options and Referrer-Policy. Changes the SEC-01 fix may need become a domain and a route on infrastructure MarDoc already runs. Fixing SEC-01 is what stage 2, longer sign-ins, waits for.

Evidence

The owner's note of 2026-10-22, the SEC-01 finding, RK-1, and Cloudflare's docs for _headers. How much the headers help SEC-01 is a hypothesis until the SEC-01 design uses them. RK-1

02 · SituationThe site is small and Cloudflare already fronts it; sign-in is designed but not built

Hosting today: deploy.yml builds with next build on every push to main and publishes out/ to GitHub Pages, with the custom domain set by public/CNAME. Cloudflare proxies the zone, and responses carry cf-ray and x-github-request-id. GitHub Pages also answers www.mardoc.app with a 301 to the apex (review check, 2026-10-23). The apex has four proxied A records pointing at GitHub Pages, and www is a proxied CNAME to mardoc-app.github.io (read through the API, 2026-10-27). SSL mode is Full, not Full (strict): GitHub Pages answers Cloudflare with a *.github.io certificate, so that hop doesn't check the origin's identity. Serving from a Worker removes the hop. deploy.yml CNAME Q-5

The build fits easily: a local out/ held 80 files and 5.0 MB (measured 2026-10-23 on the lead's machine). The Free plan allows 20,000 asset files per version and 25 MiB per file. Cloudflare limits

Sign-in: ADR 0001 puts the Auth Worker on the route mardoc.app/api/auth/*, with GitHub Pages serving everything else. The owner reported SP-1 as passing on 2026-10-21, but its results aren't in the report yet. SP-1 used a disposable Worker with no static assets and no /* route. The L1 has the owner deploy the Auth Worker from a tagged commit, with nothing deploying it automatically (A-17, Q-25). ADR 0001 SP-1 L1 requirements

What headers can and can't do: a Content-Security-Policy is defence in depth; it does not by itself close SEC-01, whose details are kept privately. A policy can break documents that rely on scripts, which is why it starts in report-only mode. A static export can't use per-request nonces, so the app's own inline scripts need hashes. CSP 3

Reused: the zone and its DNS record, the build, the e2e suite, the SP-1 probe, and the whole sign-in L1, including its separate, owner-deployed Auth Worker.

Why no automatic deploy: Cloudflare's Workers Builds creates an API token that can edit every Worker in the account and routes on every zone. A compromised build on main could therefore replace the Auth Worker, which keeps the client secret, or re-create a route. With the owner deploying both Workers, no stored token can do that. How the OAuth 2.0 sign-in works here

The flow is GitHub's web flow for GitHub Apps, an authorization code with PKCE, which GitHub marks “Strongly recommended”. It runs in the Auth Worker exactly as the L1 designs it. GitHub docs

  1. Start: Sign in with GitHub opens a pop-up at /api/auth/login. The Auth Worker makes a state value and a PKCE verifier, keeps them in a 10-minute HttpOnly cookie (F-28), and redirects to GitHub with state and the S256 challenge.
  2. Consent: the user approves on github.com and, the first time, installs MarDoc on repositories.
  3. Exchange: GitHub redirects to /api/auth/callback. The Worker checks state, then sends the code, the verifier and the client secret to GitHub, which lists the secret as required.
  4. Hand-off: the Worker returns a small page that posts the access token to the MarDoc tab once, keeps no copy, and closes.
  5. Use: the tab holds the token in memory and calls api.github.com directly. The token reaches only repositories where both the user and MarDoc have access.

The callback URL stays https://mardoc.app/api/auth/callback, so the production App needs no change. GitHub docs

How long a sign-in lasts

The 8 hours is GitHub's, and it can't be set to 12. GitHub's docs say expires_in “will always be 28800 (8 hours)”. The only alternative is to opt out of expiry, which gives tokens that never expire. GitHub docs

  • 12-hour tokens: GitHub doesn't offer them (NF-12 follows GitHub's fixed value).
  • No expiry: rejected, because a captured token would work until revoked.
  • Silent refresh, stage 2: a refresh token that lasts 6 months gets a new token unseen (NF-12), and MarDoc sets its own limit, for example 12 hours. This is the way to 12 hours. It waits for the SEC-01 fix.

What Cloudflare keeps:

  • Configuration: the public site files, the client secret, the Workers' code, versions and settings.
  • Logs: Workers Logs is on by default for new Workers, and each invocation log records the request URL. For the callback, that URL includes the code and state. The production Auth Worker turns invocation logs off (Q-31). The staging Auth Worker keeps them, with the test App, to measure CPU time. The Site Worker runs no code, so it writes no invocation logs. Cloudflare docs
  • Never stored by MarDoc's design: tokens and documents. Tokens pass through the Auth Worker in transit only, and documents never touch it.

Cloudflare remains a party in the credential path. RK-2 is unchanged because no pipeline holds a Cloudflare token: only the owner deploys the code that sees tokens. RK-2

What the user sees, and why it beats a PAT: the user never makes, copies or pastes a secret. They approve on GitHub's own page, which names MarDoc and what it can do. Settings shows who they are signed in as and when the sign-in ends. GitHub lists MarDoc under Settings → Applications → Authorized GitHub Apps, where the user can revoke it. GitHub docs

04 · DecisionOne direction to approve, two reversing proofs, and a way back at every step

1 / The same site, from a staging Worker (reversing, SP-4)

next.mardoc.app gets a proxied record of the same type as the apex and a staging Site Worker on the route next.mardoc.app/*, the same mechanism as production. The SP-1 test-App Auth Worker sits on next.mardoc.app/api/auth/*, with APP_ORIGIN and the callback URL set for that hostname. Wildcard matching stays off on both Apps (A-11).

Pass: every file matches the GitHub Pages copy. For a table of URLs (/, /index.html, /demo, /demo.html, /favicon.ico, an unknown path), each URL that returns 200 on GitHub Pages returns the same bytes from the Worker, directly or after one redirect. Unknown paths return the same 404 page. cache-control and access-control-allow-origin match. The html_handling setting is chosen from this table. The e2e suite passes. /api/auth/health reaches the Auth Worker, and a test sign-in round trip works. After 500 requests to unknown paths, the Site Worker's Metrics → Requests count in the dashboard stays at 0. If it fails: stay on GitHub Pages; ADR 0001 stands.

2 / A route moves production traffic and back (reversing, SP-5)

Canary first: a route for mardoc.app/demo* alone sends the demo page to the Site Worker. /demo answers 200 with an x-mardoc-host header. The owner then deletes the route and runs wrangler deploy again. Pass: the route stays deleted and /demo shows x-github-request-id again. Then cut-over at a quiet hour: the same check for mardoc.app/*, measuring both switch times, with each expected under 60 s†. If it fails: cut over with a Custom Domain in a planned window, which first needs the four apex A records removed. Rolling back that way means re-creating them. Cloudflare docs

3 / A policy the app runs under (shaping, after L1)

A report-only Content-Security-Policy runs through the e2e suite and sample documents. Pass rule: no reports from MarDoc's own pages once its inline scripts are allowed by hash. Reports caused by documents are listed for the SEC-01 design. If it fails: the policy changes, not the hosting decision.
