01 · WhyMarDoc gets its own response headers, one deploy, and a shorter path to longer sign-ins

GitHub Pages serves files but lets the site set no response headers, so MarDoc can't send a Content-Security-Policy, which is the main tool for containing scripts in rendered documents (SEC-01). Cloudflare's static assets accept a _headers file. Cloudflare docs SEC-01

Who benefits

Reviewers, because a header-based policy can limit what a script in a shared document can do. The owner, because the site and the sign-in code ship in one deploy from main instead of a Pages deploy plus a separate Worker.

What improves

Headers such as Content-Security-Policy, X-Content-Type-Options and Referrer-Policy on every page. A staging hostname with no users, to test each change before it reaches mardoc.app. A fix for SEC-01, which is what stage 2 (silent refresh, longer sign-ins) is waiting for, gets the tools it needs. The fix itself stays out of scope.

Evidence

The owner's note of 2026-10-22. The SEC-01 finding and RK-1 in the risk register. Cloudflare's docs for _headers. The benefit to SEC-01 is a hypothesis until the SEC-01 design uses it. RK-1

02 · SituationThe site is small and Cloudflare already fronts it; sign-in is designed but not built

Hosting today: deploy.yml builds with next build on every push to main and publishes out/ to GitHub Pages. The custom domain comes from public/CNAME. Cloudflare proxies the zone: responses carry cf-ray and x-github-request-id. deploy.yml CNAME Q-5

The build fits easily: a local out/ holds 80 files and 5.0 MB (measured 2026-10-23). The Workers Free plan allows 20,000 asset files per version and 25 MiB per file. Cloudflare limits

Sign-in: ADR 0001 chose a GitHub App and a Worker on the route mardoc.app/api/auth/*, with GitHub Pages serving everything else. SP-1 tested that route on the live zone, and the L1 design for stage 1 is reviewed; its gate row is GSI-L1 in plan.md. ADR 0001 SP-1 L1

The risk headers would help with: three viewers render HTML in srcdoc iframes with allow-scripts allow-same-origin, so document scripts run as mardoc.app. A srcdoc iframe inherits its parent page's Content-Security-Policy, so a policy on the app also applies to documents. That can protect users, or break documents that run scripts, which is why proof 1 starts in report-only mode. HtmlViewer.tsx:357 DiffViewer.tsx:1119 RepositoryReference.tsx:52 CSP 3

Reused: the Cloudflare zone and its DNS record, the build, the e2e suite, the SP-1 probe, and the whole sign-in L1: routes, cookies, callback page and session states.

03 · The piecesOne Worker serves the files without running code; only /api/auth/* runs code, and the token lives only in the tab

Cloudflare serves a request for a file from out/ straight from its asset store, without running Worker code. Those requests are free and unlimited. Setting run_worker_first to /api/auth/* sends only sign-in requests to the code. Cloudflare billing run_worker_first

Why this matters for safety: if the sign-in code ever passes the Free plan's 100,000 requests a day, those paths get a 429 and the PAT option still works, while the site keeps loading. _headers applies only to file responses, so sign-in responses set their own headers, as the L1 already specifies for the callback page. Cloudflare docs design.md

How the OAuth 2.0 sign-in works here

The flow is GitHub's web flow for GitHub Apps: an authorization code with PKCE, which GitHub “strongly recommends”. It is the L1 design unchanged; only the deployment that serves steps 1, 3 and 4 changes. GitHub docs

  1. Start: Sign in with GitHub opens a pop-up at /api/auth/login. The Worker makes a state value and a PKCE verifier, keeps them in a 10-minute HttpOnly cookie (F-28), and redirects to GitHub with state and the S256 challenge.
  2. Consent: the user approves on github.com and, the first time, installs MarDoc on repositories.
  3. Exchange: GitHub redirects to /api/auth/callback. The Worker checks state, then sends the code, the verifier and the client secret to GitHub. GitHub requires the secret even with PKCE.
  4. Hand-off: the Worker returns a small page that posts the access token to the MarDoc tab and closes. The tab holds the token in memory only.
  5. Use: the app calls api.github.com directly. The token reaches only repositories where both the user and MarDoc have access.

The callback URL stays https://mardoc.app/api/auth/callback, so the production GitHub App needs no change for the move. GitHub docs

How long a sign-in lasts

The 8 hours is GitHub's, and it can't be changed to 12. GitHub's docs say the token's expires_in “will always be 28800 (8 hours)”. The App can only opt out of expiry, which makes tokens that never expire, a worse risk than today's PATs. GitHub docs

The access token lives only in the open tab; Cloudflare keeps the client secret and the public site files

GitHub hands the access token to the Worker, the Worker passes it to the tab and keeps no copy, and the tab holds it in memory until it expires or the tab closes. The user's password never leaves github.com. Cloudflare stores the site files, which are public, and the App's client secret. design.md requirements.md

What Cloudflare keeps

  • Kept by design: the site files, which are public; the client secret; the Worker's code, versions and settings.
  • Kept by the platform: request metadata in Cloudflare's analytics and, if enabled, Workers Logs. For the callback, the URL contains the one-time code and state. Both are used up within seconds and can't be redeemed without the secret and the verifier. What Workers Logs records is checked in proof 2.
  • Never kept: access tokens, refresh tokens or documents. The Worker has no database or storage binding, and the L1 forbids logging tokens. Documents go from the browser to GitHub directly and never touch the Worker.

Cloudflare is still a party in the credential path. A compromised Worker deploy or Cloudflare account could capture tokens as they pass through. That is RK-2, unchanged by this move. RK-2

What the user sees, and why it is safer than a PAT

The user never makes, copies or pastes a secret. They click Sign in with GitHub and land on GitHub's own page, which names MarDoc and lists what it can do. Back in MarDoc, Settings shows whom they are signed in as and when the sign-in ends. GitHub lists MarDoc under Settings → Applications → Authorized GitHub Apps, where the user can revoke it at any time. GitHub docs

What it doesn't fix: while SEC-01 is open, a script in a rendered document can still take the token. It gets a token limited to installed repos that dies within 8 hours (NF-12), instead of a long-lived PAT. The headers in this proposal are a first step towards closing SEC-01.

04 · DecisionOne direction to approve, three proofs that can send us back to ADR 0001, and a one-step way back

1 / The same site from the new host

On next.mardoc.app: every file in out/ matches the GitHub Pages copy byte for byte, the e2e suite passes against the deployed site, and the baseline headers are present. A Content-Security-Policy runs in report-only mode through the e2e suite and a set of sample documents, and its reports are counted. If it fails: stay on GitHub Pages; ADR 0001 stands unchanged.

2 / Sign-in works inside the site Worker

On next.mardoc.app with the test App: the SP-1 probe passes and a sign-in round trip returns the user's login. Workers Logs shows sign-in requests under the Free plan's 10 ms CPU limit, and the dashboard counts only /api/auth/* requests as Worker requests. If it fails: the site still moves, and sign-in stays in a separate Auth Worker on its route. Cloudflare limits

3 / Cut-over and rollback each take one step

On mardoc.app at a quiet hour: adding the route mardoc.app/* makes / answer from the Worker, with no x-github-request-id header. Deleting it brings that header back within 60 s†, and /api/auth/health answers throughout. Both switch times are measured. Whether a route on the proxied record serves static assets is inferred from the docs, not yet checked. If it fails: cut over with a Custom Domain in a planned window instead. That needs the existing CNAME record deleted first, and rollback means re-creating it. Cloudflare docs
